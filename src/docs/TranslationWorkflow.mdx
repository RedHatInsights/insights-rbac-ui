# Translation Workflow

RBAC UI stores FormatJS descriptors in `src/Messages.js`, with the generated source catalog in `locales/translation-template.json` and compiled English runtime messages in `src/locales/translations.json`. Do not edit generated catalogs by hand.

## Author messages

Keep all FormatJS descriptors in `src/Messages.js`. Give each a stable `id`, English `defaultMessage`, and translator-facing `description`; do not declare descriptors beside their use.

The central file uses `defineMessages`, which FormatJS extracts. Components import its default `messages` object and reference descriptors:

```tsx
// src/Messages.js
import { defineMessages } from 'react-intl';

export default defineMessages({
  adminRole: { id: 'adminRole', defaultMessage: 'Admin', description: 'Admin role label' },
  viewerRole: { id: 'viewerRole', defaultMessage: 'Viewer', description: 'Viewer role label' },
});

// Component (relative import path varies)
import messages from 'src/Messages';
intl.formatMessage(isAdmin ? messages.adminRole : messages.viewerRole);
```

When branches differ only by count or a value, prefer one ICU message (`{count, plural, one {…} other {…}}`, `{kind, select, …}`) instead of a ternary. Never pass English words such as `'user'`/`'users'` as message values. Reused and feature-specific copy both live in the central store; keep descriptors for the same ID consistent across all uses, and use distinct IDs when copy must differ.

## ESLint

ESLint checks application JS/TS descriptors, excluding stories and tests:

- `formatjs/enforce-description`, `formatjs/enforce-default-message`, and `formatjs/enforce-placeholders` require literal context and matching `values`.
- `formatjs/no-literal-string-in-jsx` warns on hardcoded JSX text in product UI, excluding CLI and user-journey scaffolding. Existing warnings are translation debt; do not add new ones.

## Generate catalogs

After adding or changing descriptors:

```bash
npm run translations
npm run lint
```

`npm run translations` extracts descriptors from application JS/TS (sourced from `src/Messages.js`) into `locales/translation-template.json` and compiles `src/locales/translations.json`. Review both generated files and commit them with the source changes. `translations:prepare` compiles the checked-in source catalog before `npm start`, `npm run start:no-proxy`, and `npm run build`.

| Path                                | Role                                                 |
| ----------------------------------- | ---------------------------------------------------- |
| `locales/translation-template.json` | Generated English descriptors and translator context |
| `src/locales/translations.json`     | Compiled flat English runtime messages               |

## Runtime locale support

`src/locales/locale.ts` currently selects `en` unconditionally. The Storybook **Locale** toolbar demonstrates locale switching for component stories; journey stories continue using the app's English provider. The `zh-CN` demo catalog lives in `.storybook/locales/zh-CN.demo.json`, outside production catalogs. It exercises ICU messages and falls back to English for IDs it does not contain. Runtime locale selection remains a separate product change.
